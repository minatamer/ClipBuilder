SEC-02MediumConfirmed code behavior

A bot can take the few available session-start slots

Threat

Before the fix, three requests could use the shared start allowance before a bot check. Other visitors then cannot start. The attacker does not need to run AI or upload a video.

Solution

Fixed locally: verify a fresh session-start bot proof before allocating a slot. Allow only two pending checks with a five-second deadline. Later action checks stay session-bound.

Keep working: Reuse the existing challenge feature carefully. Preserve consent, source choice, action checks and the full export flow.
Evidence, limits and review notes

Evidence: The original proof issued three challenge-free grants. New tests reject invalid starts without consuming genuine slots, cover both grant routes, cancellation and allocation races, and preserve normal/replay sequencing. No paid provider or renderer dispatch is introduced.

Limit: Public impact requires an accessible enabled grant route. The current backend is loopback-bound and public paid composition remains blocked. Challenge sequencing now uses a distinct start proof; a redeemed token cannot be reused. Actual Turnstile/CSP behavior remains an owner release check.

SEC-03MediumConfirmed delivery-policy gap

One valid visitor can keep downloading the same media

Threat

Before the fix, a visitor could repeatedly fetch their preview or finished clip until expiry. Limits on simultaneous streams and processing do not limit total repeated delivery.

Solution

Fixed locally: preview and finished output share 2 GiB of delivery, 1,024 content reads and 64 metadata requests per session. Refresh and download aliases cannot refill it. Requests exceeding it stop before private media work.

Keep working: Preserve seeking, refresh, weak-network retries and repeat downloads. No “one GET” restriction or CAPTCHA on playback.
Evidence, limits and review notes

Evidence: Synthetic checks allow 16 full 24 MiB previews and eight 200 MiB downloads within the byte allowance. Boundary tests cover small ranges, shared metadata, aliases and reopening with no extra processing. A late response after Exit is cancelled before playback headers are published.

Limit: This does not expose another visitor’s clip. The risk is resource/traffic cost; actual cost was not measured. Real device/network behavior remains an owner check; failed or uncertain read reservations stay consumed.

Detailed finding · Careful plan

SEC-05MediumConfirmed lifecycle limit · Existing fallback

A crash can delay deletion of the temporary Google file

Threat

If the backend disappears after uploading a proxy, it loses its pending deletion record. Google’s file-expiry fallback then applies, rather than our normal immediate cleanup.

Solution

Accepted by you: keep the up-to-48-hour provider expiry fallback after a hard crash. Normal explicit deletion remains enforced. No recovery sweep or database is added.

Keep working: Normal explicit deletion stays. Accepting the fallback requires no code change; recovery must never delete active or unrelated files.
Evidence, limits and review notes

Evidence: Pending Google Files cleanup lives in backend memory; a replacement has no orphan inventory. The existing GCS sweep handles different storage.

Limit: Google documents Files expiry after 48 hours. Privacy copy already separates delayed removal and Google retention. No public exposure or false instant-deletion claim was established. A sweep needs verified exclusive ownership and revision safety.
